# 需求文档

> 版本：v3（2026-11-07）· 迁入正式项目 `dsh-meme-brain`
> 状态：**设计定稿，待开工**
> 相关：[决策记录](00-decisions.md) · [架构设计](02-architecture.md) · [工程契约](03-engineering-contract.md)
> 一句话：建一个**完整的表情包管理系统**——一张图从进入系统到被 AI 和人用上，全程有流程、有状态、有入口。

---

## 1. 定位

**这是一个系统，不是一次库改造。**

"库唯一"只是系统内部的一条存储约束；系统的价值在于把散落的能力串成一条完整流水线，并且**同时面向人和 AI** 提供可用入口。

| 谁 | 用什么 | 得到什么 |
|---|---|---|
| **人（你）** | Web 管理台 | 浏览、筛选、看详情、合并重复、改标注、导入导出 |
| **AI（她）** | 工具 + 服务 | 按情绪/角色/对象找图、标注、查重复 |
| **外部程序** | 本地 HTTP / MCP / 导出文件 | 把库和判断接进别的工具 |

三端共享同一份数据与同一套判断，不存在"AI 看到的"和"人看到的"不一致。

## 2. 现状与缺口

### 2.1 现在谁负责什么

| 环节 | 谁在做 | 问题 |
|---|---|---|
| 从 QQ 收图 | Aurabot 内置表情模块 + `gif-stickers` 模块 | 两套逻辑重叠，都在往自己的库写 |
| 解析 | 内置模块只取尺寸；起名靠一次视觉调用 | 没有格式矩阵、没有帧/透明/文字等结构化解析 |
| 去重 | 只比字节 md5 | 近似重复漏掉（已实测 1 例） |
| 入库 | Aurabot 自己的 `stickers/` | 与 dsh-meme 的 24 张互不可见 |
| 分析 | 只有一句 `caption` + 最多 3 个标签 | 无角色、无维度、无文字 |
| 检索 | `matchSticker` 名字/标签字面匹配，未命中随机抽 | 就是"选错图"的根源 |
| 人用界面 | Aurabot 的 `/stickers` 面板（改名/删除） | 只能看和改名字，不能筛选、不能看分析 |
| AI 用 | `<sticker:名字>` | 看不到分数，无法按情绪挑 |

### 2.2 证据（只列实际发生的）

| 编号 | 现象 | 证据 |
|---|---|---|
| **P1** | 近似重复入库 | 2026-11-07 用新解析器扫描 Aurabot 库 **288 张**：**14 组**近似重复（md5 不同、dHash 距离 0–4），约占总数的 10%；另有 **3 个同 md5 的重复文件**（`collected-` 与 `manual-` 各存一份）。11-05 时只有 1 组——**问题随收录量在放大** |
| **P2** | 选错表情 | 天涯群 55 条审核意见中 **7 条**明确说不合适（如「抢我饭碗」配打人图） |
| **P3** | 认不出角色 | 名字全是外观描述（`呆萌施法的猫耳少女`、`薄荷拳击`），抽查两张均无身份信息 |
| **P4** | 两库并存 | dsh-meme 24 张 + Aurabot 153 张，跨库 dHash 比对 0 重叠 |

### 2.3 真正的缺口

不是"库太多"，而是：**没有任何一处能完整走完一张图的处理流程**。

- 收图的不管分析，分析的不管检索，检索的不管界面；
- 人想纠正一张图的判断，没有入口；
- 想看"库里到底有哪些类别的图"，只能靠翻文件名。

## 3. 系统全景

### 3.1 流水线

```
 ①接入          ②解析           ③去重          ④入库
  QQ 消息   →   格式/帧/尺寸  →  md5 精确   →  唯一库写入
  手动上传       透明/文字       感知哈希        命名/分类
  目录扫描                       语义(角色+字)   来源记录
  导入包
       ↓
 ⑤分析          ⑥索引           ⑦消费
  角色识别   →   多维倒排   →    AI 工具（找图/标注）
  多维评分       全文检索        管理台（浏览/编辑）
  文字提取       状态队列        导出（ZIP/JSON/API）
```

### 3.2 一张图的生命周期

| 状态 | 含义 | 出边 |
|---|---|---|
| `incoming` | 刚收到，尚未解析 | 解析成功 → `parsed`；失败 → `failed` |
| `parsed` | 有格式/尺寸/帧/哈希 | 去重命中 → `duplicate`；未命中 → `stored` |
| `stored` | 已入唯一库 | 分析完成 → `analyzed` |
| `analyzed` | 有分数/角色/文字 | 可直接被检索 |
| `duplicate` | 被判为某张的重复 | 合并 → `retired`；人工否定 → `stored` |
| `failed` | 解析或分析失败 | 重试 → 上一状态；放弃 → `retired` |
| `retired` | 已删除或已合并 | — |

状态必须可在管理台看到并筛选。

### 3.3 三种出口，一套数据

```
                    ┌──► AI：工具（find/annotate/dedupe）
 系统数据（唯一） ──┼──► 人：管理台（浏览/筛选/编辑/导入导出）
                    └──► 外部：HTTP API / MCP / 导出文件
```

## 4. 功能需求

> P0 = 首版必须；P1 = 第二版；P2 = 观察后再做

### 4.1 接入（Ingest）

| ID | 需求 | 优先级 | 验收 |
|---|---|---|---|
| FR-I1 | 从 QQ 群/私聊自动接收表情与图片 | P0 | 群里发图，系统在 N 秒内记录 |
| FR-I2 | 手动上传单张/多张 | P0 | 管理台拖入文件后出现在列表 |
| FR-I3 | 扫描目录批量导入 | P0 | 指向一个文件夹，扫描出全部图片 |
| FR-I4 | 导入外部包（ZIP / 其它插件图库） | P1 | 导入后条数正确、无重复 |
| FR-I5 | 每条记录保留来源（QQ 群号/私聊/手动/导入包） | P0 | 详情页可见 |
| FR-I6 | 超大/损坏文件跳过并记原因 | P0 | 失败列表里能看到原因 |

### 4.2 解析（Parse）

| ID | 需求 | 优先级 | 验收 |
|---|---|---|---|
| FR-P1 | 按魔数识别格式（jpg/png/gif/webp/apng），不信扩展名 | P0 | 扩展名与真实格式不符时按真实处理 |
| FR-P2 | 读出尺寸、字节数、是否动图、帧数 | P0 | 详情页显示 |
| FR-P3 | 检测透明通道并记录 | P0 | 带 alpha 的图被标记 |
| FR-P4 | 计算三帧感知哈希（首/中/末），透明先合成白底 | P0 | 同一图重压后哈希不变 |
| FR-P5 | 提取图上文字（OCR） | P1 | 带字表情能读出文字 |
| FR-P6 | 解析失败有明确原因并进入失败队列 | P0 | 失败队列可查看、可重试 |

### 4.3 去重（Dedupe）

| ID | 需求 | 优先级 | 验收 |
|---|---|---|---|
| FR-D1 | **入库前**判重：精确 md5 → 感知哈希 | P0 | 同一张连发 3 次只入库 1 张 |
| FR-D2 | 多帧比较，不只看首帧 | P0 | 首帧相同、后段不同的两张不被判重 |
| FR-D3 | 阈值可配置，且不误伤同模板不同内容 | P0 | 库内最近的非重复对（距离 11）不被判重 |
| FR-D4 | 判为重复时建立"重复于哪张"的关联，可追溯 | P0 | 详情页能看到"疑似与 X 重复" |
| FR-D5 | 支持全库重复报告 | P1 | 一条命令/按钮输出重复簇 |
| FR-D6 | 允许人工否决"这是两张不同的图" | P1 | 否决后不再判重 |
| FR-D7 | 语义去重（同模板不同台词） | P2 | 观察实际需要再做 |

### 4.4 入库（Store）

| ID | 需求 | 优先级 | 验收 |
|---|---|---|---|
| FR-S1 | 全系统只有一处存图片字节 | P0 | 全盘只有库目录有表情图 |
| FR-S2 | 存储后端可配置（自管目录 / 外部图库） | P1 | 切换后端不影响已有数据读取 |
| FR-S3 | 文件名、md5、路径三者可互相反查 | P0 | 任给其一能查到整条记录 |
| FR-S4 | 入库保留原始字节（动图不转码） | P0 | GIF 帧数与原件一致 |
| FR-S5 | 删除/合并是软删除，可恢复 | P1 | 删除后能在回收站找到 |
| FR-S6 | 库可整体导出/导入（含元数据） | P1 | 导出再导入，记录不丢 |

### 4.5 分析（Analyze）

| ID | 需求 | 优先级 | 验收 |
|---|---|---|---|
| FR-A1 | 识别图中角色：名字 + 把握度 + 允许"未知" | P1 | 20 张抽样人工核对命中 ≥80% |
| FR-A2 | 全局角色表，跨来源通用 | P1 | 新增角色后任何入口可检索 |
| FR-A3 | 七维评分：情绪价、强度、攻击性、亲密、抽象度、指向、场景 | P1 | 每张可读出各维数值 |
| FR-A4 | 评分按固定锚点，可重跑，同图两次偏差 ≤0.1 | P1 | 抽 10 张跑两遍比对 |
| FR-A5 | 记录每条分析用的模型与时间，便于追责/重跑 | P1 | 详情页可见 |
| FR-A6 | 分析失败进队列，可重试，不阻塞其它图 | P0 | 失败不影响新图入库 |
| FR-A7 | 人工可覆盖任何分析结果，并标记"人工已确认" | P0 | 覆盖后 AI 不得再改，除非强制重跑 |

### 4.6 检索（Retrieve）

| ID | 需求 | 优先级 | 验收 |
|---|---|---|---|
| FR-R1 | 按角色、情绪区间、指向、场景、来源筛选 | P0 | 组合条件返回正确集合 |
| FR-R2 | 关键词搜（名字/描述/标签/图上文字） | P0 | 搜"干饭"能命中 |
| FR-R3 | 排序（最新、最常用、分数） | P1 | 排序结果符合预期 |
| FR-R4 | 找不到就返回空，不随机兜底 | P0 | 检索无结果时返回空数组 |

| FR-U3 | 单张编辑：名字 / 角色 / 分数 / 文字 | 命令 + 界面 | P0 | 改动后立即能检索到 |
| FR-U4 | 批量操作（设角色 / 打标签 / 删除 / 导出） | 命令 + 界面 | P1 | `/meme bulk --set-character=凯露 --ids=...` |

| FR-U6 | 待办队列（未分析 / 低置信 / 疑似重复 / 失败） | 命令 + 界面 | P1 | `/meme todo` 分类计数并可处理 |
| FR-U7 | 角色表管理 | 命令 + 界面 | P1 | `/meme char add/rm/list` |
| FR-U8 | 导入导出（ZIP / JSON） | 命令 + 界面 | P1 | `/meme export` / `import` |
| FR-U9 | 状态统计 | 命令 + 界面 | P2 | `/meme stats` |
| FR-U10 | 独立管理页面（侧栏入口 + 网格 + 详情抽屉） | **仅界面** | P1（M8） | 全部数据来自命令端点，页面内无业务计算 |
| FR-U11 | 动图在列表中可播放 | 仅界面 | P2（M8） | — |

## 5. 管理能力设计要点（命令优先，界面后置）

> 按 [ADR-0005](00-decisions.md)：**M3 只做命令，本节是 M8 的界面规格**。命令与界面调用同一批端点，因此界面落地时不允许新增任何业务逻辑——本节描述的是"最终长什么样"，不是"第一步做什么"。

### 5.1 页面入口（已确认可行）

Web 端有两个可用槽位：

- `sidebar.panellist` — 侧栏全局图标，注册一个 id + 图标
- `main`（键控）— 主面板按 id 渲染，当前只被 `conversation` 占用

所以做一个**顶级页面**是标准做法：侧栏加"表情包"图标 → 点击切到 `main` 的自定义面板。

配置页可另用 `settings.section`。

### 5.2 页面结构

```
┌ 表情包 ─────────────────────────────────────────────┐
│ [搜索] [角色▾] [情绪▾] [指向▾] [来源▾] [状态▾]  ⟳    │
├─────────────────────────────────────────────────────┤
│ ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐                  │
│ │缩略│ │缩略│ │缩略│ │缩略│ │缩略│   ← 网格，动图会动  │
│ └────┘ └────┘ └────┘ └────┘ └────┘                  │
│  凯露    干饭    熊猫头   ??     睡觉                 │
├─────────────────────────────────────────────────────┤
│ 已选 3 张  [设角色] [打标签] [合并] [导出] [删除]     │
```

点任一张 → 右侧抽屉：

```

─────────────

```

### 5.3 待办队列

管理的核心不是"看全部"，而是"处理待办"：

| 队列 | 内容 | 操作 |
|---|---|---|
| 未分析 | 刚入库还没跑分析的 | 批量分析 |
| 低置信 | 角色把握度 `low` 的 | 人工确认 |
| 疑似重复 | 哈希距离落在灰区的 | 合并 / 否否 |
| 解析失败 | 打不开的 | 查看原因 / 删除 |

## 6. 非功能需求

| ID | 需求 | 指标 |
|---|---|---|
| NFR-1 | 采集处理延迟 | 单张（不含分析）≤ 300ms |
| NFR-2 | 分析成本 | ≤ ¥0.005/张；可批量、可暂停 |
| NFR-3 | 索引可重建 | 删索引后无需重下图片 |
| NFR-4 | 界面性能 | 1000 张缩略图滚动不卡（虚拟列表） |
| NFR-5 | 数据可迁移 | 全库导出后可在另一台机器还原 |
| NFR-6 | 幂等 | 重复导入/重复分析不产生脏数据 |
| NFR-7 | 可观测 | 每个阶段有计数与失败原因 |
| NFR-8 | 隐私 | 图片不出本机（分析调用除外，可关） |
| NFR-9 | 幂等/可回滚 | 每个写操作要么幂等，要么有撤销路径 |
| NFR-10 | 迁移安全 | 数据迁移带版本号、迁移前自动备份、支持 `--dry-run` |
| NFR-11 | 失败可数 | 所有失败落到稳定错误码，并计入 `doctor` 队列 |
| NFR-12 | 无界面可验证 | 任何功能都有一条不依赖 Web 界面的验证路径 |

## 7. 约束（已核实）

| ID | 约束 | 影响 |
|---|---|---|
| C-1 | Aurabot 的 `hub.js:616` 依赖 `stickers` 服务对象；模块不加载会抛错 | 若接管 Aurabot，只能关行为不能禁用模块 |
| C-2 | Aurabot 扩展模块是单文件 `.mjs`，装不了 npm 依赖 | 解析/哈希必须在插件侧 |
| C-3 | 解码依赖 `sharp`（原生二进制，约 30MB），无纯 JS 回退 | sharp 不可用时降级为"只索引不解析"，见 ADR-0015 |
| C-4 | dsh-meme 已卸载（ADR-0016/0019），其 24 张官方图不在本机 | 需要时临时装回 `dsh-meme@0.1.76` 导出 |
| C-5 | 同一会话不得并存第二套表情能力（ADR-0019） | 新装插件前检查是否注册表情相关工具 |

## 8. 验收总纲

系统"可用"的最低标准：

1. 群里发 3 次同一张图 → 库里 1 张，另外 2 次在日志里是"重复"
2. 群里发一张新图 → 管理台 30 秒内出现，状态从 `incoming` 走到 `stored`
3. 管理台能按角色筛出图，点开能看到六维分数
4. 人工把一张的角色改掉 → 立刻能按新角色搜到
5. 删掉索引 → 一条命令重建，数据不丢
6. AI 能按"生气 + 攻击性低"找到图并发出
7. 全库导出 → 清空 → 导入，条数与标注一致

## 9. 里程碑（按流水线切）

| # | 内容 | 交付后可验证 |
|---|---|---|
| M0 | 插件骨架：可安装、有命令壳、`doctor` 能跑 | `meme doctor` 输出空库体检报告 |
| M1 | 解析 + 哈希 + 判重（离线） | 固定夹具全绿；对现有库跑出重复簇 |
| M2 | 存储 + 索引 + 状态机 + 重建 | 扫描目录后 `doctor` 各项相等 |
| M3 | **管理命令集**（list / show / annotate / dupes / todo / export） | 上述命令全部可用，不需要界面 |
| M4 | **最简界面**（网格 + 详情 + 单张编辑） | 界面数据全部来自命令端点，页面无业务计算 |
| M5 | 分析（七维评分 + 文字）+ 失败队列 | 新图自动分析，失败可重试、可计数 |
| M6 | 角色表 + 标注闭环 + 检索 | 按角色/场景找到图，人可纠错 |
| M7 | AI 工具 + cordis 服务 | QQ 里能按条件选图 |
| M8 | 采集接入（QQ）+ 判重前置 | 群里发的图自动进系统 |
| M9 | 完整界面（批量 / 待办 / 动图）+ 导入导出 + HTTP | 全部通过端点取数，数据可迁移 |

> 排序原则：**命令（M3）先于界面（M4）**，最简界面先于分析（M5）——先让人能看到已有数据，分析结果才有地方显示；完整界面与导入导出放到最后。
